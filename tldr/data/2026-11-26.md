### Deep Dives

[### Distributed primary keys (44 minute read)](https://tapoueh.org/blog/2026/11/distributed-primary-keys/?utm_source=tldrdata)

Reproducible benchmarks compare primary key strategies for multi-region PostgreSQL across index size, WAL overhead, and failover safety. UUIDv7 is efficient and needs no coordination. Regional sequences can collide after failover, timestamp-based IDs are vulnerable to clock rollback, and composite keys simplify replication filtering but use more storage.

[### How Grab built Scarlet: the AI teammate that turns a Slack message into a production data pipeline (13 minute read)](https://engineering.grab.com/how-grab-built-scarlet-blog?utm_source=tldrdata)

Grab's AI agent, Scarlet, turns Slack messages and Jira tickets into data pipeline changes, checks the resulting data against production, and opens merge requests for engineers to review. After Grab introduced reusable, team-specific instructions and automated data checks, the share of Scarlet's merge requests that engineers merged rose from about 50% in May to over 85% in September.

[### Backfilling Tens of Billions of Rows Next to Live Logical Replication (Part 2) (10 minute read)](https://stormatics.tech/blogs/postgresql-logical-replication-backfill-migration-part-2?utm_source=tldrdata)

A live PostgreSQL migration moved tens of billions of rows using parallel COPY, fixed ID ranges, and resumable checkpoints. Broken WAL archiving filled the target's disk, while subscription lag retained WAL on the source until streaming = parallel cleared the backlog. Missed updates and costly joins showed why reconciliation needs checks for both correctness and performance.

[### Where Agents Meet the Browser: Building a Browser-Native Agent (17 minute read)](https://www.linkedin.com/blog/engineering/ai/where-agents-meet-the-browser-building-a-browser-native-agent?utm_source=tldrdata)

LinkedIn built an internal AI agent that works across tools in employees' existing Chrome sessions, turning incident threads into tickets and documents into slide decks. It uses structured page data to cut token usage and tool-specific playbooks to improve reliability, while showing its actions and linking to evidence so users can verify the work.

[### Legible first: how T2 built AI on what it already owned (5 minute read)](https://www.linkedin.com/pulse/legible-first-how-t2-built-ai-what-already-owned-christelle-young-ktopc/?utm_source=tldrdata)

T2 Tea consolidated data from 14 systems into one warehouse and built a semantic layer with 243 metrics, letting off-the-shelf AI models retrieve only the data and business rules each question needs. T2 reports spending about A$30 per seat per month and completing a channel analysis in about an hour that previously took consultants weeks.

[### 5 Lessons in AI Context Engineering: Why More Context Is Not Better (10 minute read)](https://engineering.salesforce.com/5-lessons-in-ai-context-engineering-why-more-context-is-not-better/?utm_source=tldrdata)

Salesforce's Help Agent must work out what a customer owns and is entitled to, with lookups under 200 milliseconds at the median. More data was not the answer. The team resolves relationships, business rules, and access ahead of time into Data 360 data graphs served by one lookup. Warehouse views had taken 7 to 30 seconds for one scoring workload.

[### Unclean leader election: Kafka trolley problem where you always end up pulling the lever (5 minute read)](https://aiven.io/blog/kafka-unclean-leader-election?utm_source=tldrdata)

When no in-sync replica remains available, Kafka can sacrifice durability to restore availability by electing an out-of-sync replica, potentially losing acknowledged writes. Kafka 4.0's Eligible Leader Replicas (ELR) can avoid this trade-off in certain failure scenarios. The decision to prioritize availability over durability should be made at the topic level, based on business requirements, rather than during an outage.

[### Orderbook-lakehouse (GitHub Repo)](https://github.com/vanalex/orderbook-lakehouse?utm_source=tldrdata)

Orderbook Lakehouse is a fully local, Docker-based reference architecture for incremental market-data processing using Apache Iceberg, Apache Polaris, Spark (Scala), Redpanda Connect, and SeaweedFS. HTTP events flow through Bronze, Silver, and Gold Iceberg tables to produce order-book state and trading analytics. Iceberg snapshots enable incremental processing and idempotent recovery, while Polaris coordinates atomic metadata commits. The architecture demonstrates reliable, restartable lakehouse pipelines without managed cloud infrastructure.

Hardwood, the lightweight, dependency-free Parquet library for the JVM, introduces parallel file writing and direct S3 uploads with multipart support. The release candidate adds ALP encoding for more compact floating-point storage, field IDs for lakehouse interoperability, and a redesigned read scheduler delivering up to 1.8× faster full scans than Hardwood 1.0. These improvements position Hardwood as a high-performance alternative for JVM applications that need direct Parquet access without Hadoop dependencies.

### Miscellaneous

[### dbt Evals: Our First Foray into Data Agent Management (8 minute read)](https://github.com/dbt-labs/dbt/discussions/17168?utm_source=tldrdata)

dbt Evals is a framework that asks analytics agents the same questions across multiple runs and checks their answers with SQL tests, classifiers, or LLM judges. The goal is to catch accuracy regressions when data models or metrics change, though the initial design tests a configurable stand-in for the production agent.

[### Compaction Was On. It Never Ran. (10 minute read)](https://blog.dataengineerthings.org/compaction-was-on-it-never-ran-427efdc02794?utm_source=tldrdata)

Benchmarking DuckDB-based duckgate against Athena exposed a small-file problem: DuckDB was up to 25x slower on an Iceberg table containing just 440K rows spread across thousands of tiny Parquet files. Hourly partitioning created excessive fragmentation, while AWS Glue compaction was enabled but never executed. DuckDB 2.0's asynchronous remote Parquet I/O narrowed the performance gap to roughly 4×, but the fundamental lesson remains: table layout and effective maintenance can matter more than query engine selection.
