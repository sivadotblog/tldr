### Deep Dives

[### The 2026 Cloud Data Warehouse Benchmark (Website)](https://warehouse-benchmark.estuary.dev/?utm_source=tldrdata)

At 100 GB, MotherDuck led in single-user speed and cost (235 ms, $0.00124/query), Fabric served 100 concurrent users under five seconds for $5.76/hour, and ClickHouse failed 20.4% of single-user runs. Databricks had the smallest latency increase from 1 GB to 1 TB (3.7x versus MotherDuck's 30x), with tuning and autoscaling disabled throughout.

[### The paper that split the database in four: inside Azure SQL Database Hyperscale, aka Socrates (8 minute read)](https://devblogs.microsoft.com/azure-sql/the-paper-that-split-the-database-in-four-inside-azure-sql-database-hyperscale-aka-socrates/?utm_source=tldrdata)

Azure SQL once kept four full copies of each database, which capped practical size at around 4 TB. The 2019 Socrates paper separated the log from storage, so durability and availability could scale apart. This change in approach let Hyperscale reach 100 TB, halve storage copies, and restore a 50 TB database in minutes.

[### How JD.com Built a Lakestream with Apache Fluss and Apache Hudi (8 minute read)](https://fluss.apache.org/blog/how-jd-built-a-lakestream-with-fluss-and-hudi?utm_source=tldrdata)

JD replaced parallel streaming and batch training-data pipelines with a staged migration: write once to Fluss, tier to Hudi, and union fresh plus historical reads. The difficult part is consistency: workers coordinate a single Hudi commit per tiering round and report matched stream offsets only after it completes. That pattern enables rollback-safe catch-up, but leaves schema evolution and dynamic bucketing unresolved.

[### Best Practices for Single Row Lookups (Point Queries) (11 minute read)](https://datafusion.apache.org/blog/2026/10/24/point-queries?utm_source=tldrdata)

DataFusion can perform surprisingly well on point lookups when tuned for retrieval instead of analytics. The biggest gains came from storage layout and execution choices that minimize unnecessary work, such as sorted Parquet files, right-sized row groups, metadata caching, and prepared statements. The broader lesson is that analytical engines can serve low-latency reads if the workload is designed deliberately.

### Opinions & Advice

[### Getting an analytics agent from 50% to 96% accuracy (9 minute read)](https://benchouse.ai/blog/getting-an-analytics-agent-from-50-to-96?utm_source=tldrdata)

Benchouse improved nao's accuracy from 49.6% to 88.2% by switching from Sonnet to Opus, then reached 96.5% with better context. The key fixes clarified business metrics, removed ambiguous terminology, and told the agent to use agreed calculations before suggesting alternatives.

[### The Benchmarking Crisis (8 minute read)](http://databasearchitects.blogspot.com/2026/10/the-benchmarking-crisis.html?utm_source=tldrdata)

AI code generation is helping database engines game ClickBench. One, pgrust, groups strings by hash value alone, caches predicates the benchmark repeats, and on one query skips most of the data. Any benchmark stops being useful once systems optimise for it, and vibe-coded engines have no customers to keep them honest.

[### PrivacyLib: Privacy Controls at the Data Access Boundary (12 minute read)](https://engineering.fb.com/2026/10/27/security/privacylib?utm_source=tldrdata)

Meta built PrivacyLib to enforce privacy rules at the moment data is accessed, replacing one-off integrations with shared controls that work across many systems. The key lesson is to normalize diverse data platforms into a small set of common operations, which makes policy enforcement reusable, scalable, and adaptable enough to extend from traditional infrastructure to AI agents.

It runs thousands of tenants in one process, metering CPU, memory, and disk per query, and its benchmark used 46% less disk than Postgres 18.
